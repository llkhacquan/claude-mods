Session Memory Claude Code mod · in development

Your sessions already learned it. Keep it.

Every Claude Code session ends with lessons in it: a root cause you proved, a rule you set, a tool that lied. Session Memory reads each session, keeps the few lines that matter, and files them as info with the sessions they came from. The next session sees the info and how often it was said, and opens the proof only when it needs it.

What it is

A shared memory that grows from your sessions, not from notes you write.

A Claude Code mod. It reads each session after the fact, pulls out info (decisions, rules, root causes, gotchas), and keeps one copy of each piece with a list of the sessions that said it. Repos you put in one group share the same memory; worktrees count as their repo.

  • infoOne line of text. No "fact" label: it is only as strong as its refs.
  • refsEach session that said it, who said it (you or the agent), when, and a short quote.
  • topicsA tree per group. At most 30 entries per level, three levels deep.
  • toolsmemory_open, memory_refs, memory_search. Claude calls them on its own when a question touches a topic.

No fixed bar for "true". Claude sees the count, who said it and when, and judges.

Why

The lessons are already in the transcripts. Nobody reads them again.

Hand-written memory misses most of it

CLAUDE.md and memory files hold what someone stopped to write down. The rest of a session's lessons stay in a transcript nobody opens, and Claude Code deletes transcripts after 30 days by default.

One repo is too small

Built-in memory is per project folder. A rule set in one backend repo, or a worktree of it, never reaches the next repo where it applies.

Approving every item does not scale

A review queue for each extracted line turns into a chore and gets skipped. Instead, info earns weight by coming back: in 20 sampled sessions, one merge rule showed up in 5 of them under 5 different wordings.

Counts, not verdicts

A label like "fact" hides how sure anyone is. A ref list keeps the evidence: you said it five times, or the agent guessed it once. The model reading it can weigh that.

Context is expensive

Loading everything would crowd out the work. Only the top level is always visible; topics and proof load when a question needs them.

Reading is cheap

Text is under 1% of a transcript. The rest is tool output that is dropped before any model sees it, so one small model call per session is enough.

Pipeline

Slice, extract, reconcile, file, serve.

1 sliceKeep prompts, replies, summaries, failing commands. Drop reads, listings, thinking. Redact secrets.
2 extractOne model call lists the info in the new part of the session, each with who said it and the lines it came from.
3 reconcileMatch by meaning against what is stored: same info adds a ref, new info gets filed under a topic.
4 fileAppend items and refs; split a topic past 30 entries. Then move the session's cursor.
5 serveThe next session gets the top level in the memory_open tool description and drills down from there.

How refs are counted

Your word counts. The agent echoing it back does not.

  • refSame info from a new session. The count grows.
  • newNew info, filed under the topic it fits; existing topic names are reused.
  • echoThe agent repeating info it was just shown. Kept, not counted, so loaded info cannot inflate itself.
  • confirmClaude states loaded info and you say OK: a ref from you.
  • rejectYou say no or correct it: an "against" ref, and the correction becomes its own item, linked as a conflict.
When it runs

Inside the session, at the moments that matter.

No daemon, no cron. The mod hooks the session itself and only reads what is new since its last pass.

turn.complete

Starts a 10 minute idle timer. A new turn cancels it. When it fires, the new part of the session is processed.

session.compact

Flush before compaction. Detail that the summary is about to drop gets read first.

session.end

Exit, clear, worktree removal or handoff: the last turns are processed before the session goes.

session.start

Sweeps sessions that died without an end event (crash, kill -9), one at a time under a lease.

Guard rails

Nothing leaves unredacted, nothing counts twice.

Secrets out first

Keys, tokens, JWTs, private key blocks, *_KEY= lines and URL passwords are redacted in the slicer, before any text leaves the machine.

You can undo

/memory-forget drops an item. It comes back only if you say it again.

Run twice, write once

Each processed slice is recorded with the write, so a retry skips it. A session votes once per item, so a stray re-run never adds weight.
